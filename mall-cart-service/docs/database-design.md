# 购物车服务数据库设计（DDD + Flyway，项目初始化阶段）

## 1. 服务边界与数据归属

- `cart-service` 负责普通用户的**待购 SKU 清单和数量**，提供（未来的）查询、添加、修改数量、删除、清空能力。
- 一名 IAM **普通用户账号**至多拥有一辆购物车；购物车项仅属于该购物车。IAM 账号与 merchant-service 商家主体不是同一对象。
- 商品名称、SKU 规格、实时售价、商家归属、商品上下架状态由 `product-service` 管理；购物车不复制商品资料，也不作为交易定价的权威来源。
- 实有、可用、锁定库存属于 `inventory-service`；**加入购物车绝不锁定库存**。
- 交易订单及商品成交快照属于 `order-service`；订单提交时必须重新校验价格、可售状态、库存等条件。
- `cart.account_id` 和 `cart_item.sku_id` 为**跨服务逻辑引用**，不建立跨数据库外键。

## 2. 两张业务表

| 表 | 主要字段 | 意义 |
| --- | --- | --- |
| `cart` | `id`、`account_id`、`version`、`created_at`、`updated_at` | 用户购物车聚合根；每个账号仅 1 行 |
| `cart_item` | `id`、`cart_id`、`sku_id`、`quantity`、`version`、时间字段 | 聚合内待购项，按 SKU 唯一 |

Flyway 自动生成的 `flyway_schema_history` 不属于业务表。

```text
iam-service: iam_account.id
        │ 逻辑 account_id（跨服务无 FK）
        ▼
     cart (1) ──────< (N) cart_item
                           │ 逻辑 sku_id（跨服务无 FK）
                           ▼
                product-service: product_sku.id
```

## 3. 关键唯一性与数量约束

- `uk_cart_account(account_id)`：同一账号不允许重复创建多个购物车，即使两个请求并发发生。建表约束并不替代未来业务层的冲突恢复处理。
- `uk_cart_item_cart_sku(cart_id, sku_id)`：同一个购物车中的同一 SKU 只出现一条记录；再次加入应按未来明确的数量策略更新已有行，不能插入第二条。
- `ck_cart_item_positive_quantity`：数量必须大于 0；如果前端将数量改为 0，后续应用服务应把它解释为删除购物车项，不保存 0。
- `fk_cart_item_cart`：购物车项必须挂到本服务内已存在的购物车；禁止直接删除仍有购物车项的聚合根。
- `version` 为未来乐观锁或条件更新预留，数据库不自动递增；业务操作需要在**单个本地事务**内维护版本号和修改时间。

## 4. 为什么不保存价格、库存和商家？

- **当前价与加入时价格可能不同。** 购物车仅存 SKU ID 和数量，查询显示时根据商品服务获取当前商品信息；订单提交时重新校验，并由订单服务形成**不可变交易快照**。
- **购物车不是库存预占。** 商品可以加购但后续售罄、下架或商家禁用，此时不能提交为有效订单；订单服务需再次校验，不能把购物车数据当作已锁定资源。
- SKU 可以通过商品服务找到 SPU 和商家经营主体。购物车表不再冗余 `product_id`、`merchant_id`，避免产品/商家归属的重复数据不一致。
- 此阶段不额外建商品名称快照表、购物车价格流水表、商家镜像表。

## 5. 购物车后续用例的数据库操作原则（当前未实现）

1. **查询**：根据已认证的当前用户账号 ID 找到 `cart`，查询其 `cart_item`，批量读取 SKU 的最新展示信息。
2. **添加**：未有购物车时创建；同一 SKU 已存在时更新数量（是累加还是覆盖需在具体接口设计时明确），同时处理并发唯一键冲突。
3. **修改数量**：使用条件更新/乐观锁防止多端并发修改丢失更新，校验正整数与业务上限。
4. **删除与清空**：只允许当前账号操作自己的购物车，删除相关 item；不因此创建订单、扣库存或清理其他账号数据。
5. **提交订单后**：只有订单服务确认接受合法交易之后，才由合法流程清理已提交的对应购物车项。若将来允许部分勾选，应只删除本次成功提交的项，不应盲目清空整车。

**注意：** MySQL 唯一约束无法阻止同一次“数量累加”请求因重试执行两次；若接口定义为数量累加，后续应引入可重复识别的请求键或把操作改成幂等的数量设置。当前未建额外幂等操作表，因为业务需求尚未要求购物车操作级历史幂等。

## 6. 本次没有假定的业务范围

- 不包含购物车跨账号合并、游客购物车、多购物车、商品批量分组、勾选结算、优惠券、运费、促销价、商品失效通知、购物车永久审计、订单历史等功能。
- **是否支持勾选部分商品提交订单，目前原始业务需求未明确。** 本期数据库没有 `selected` 字段；明确需求后再通过新增 Flyway 迁移演进，不建议凭空添加。
- Redis 可在后续优化查询或会话，但**MySQL 是本期购物车持久化真相源**。这与 Flyway 维护 schema 的目标一致。
- 未实现接口、业务聚合模型、领域行为、Repository/Mapper/PO、远程客户端或自动购物车数据修复。

## 7. Flyway 版本与环境初始化

- `V2026110301__create_cart.sql`：创建购物车聚合根表。
- `V2026110302__create_cart_item.sql`：创建购物车项与内部外键。
- 执行 `docs/create-database.sql` 建立空库 `mall_cart`；应用启动自动执行上述脚本，并建立 `flyway_schema_history`。
- Flyway 使用 `baseline-on-migrate: false`、`validate-on-migrate: true`、`clean-disabled: true`；不要擅自覆盖历史版本。
- 如果之前旧版 cart-service 已经在 `mall_cart` 跑过 Flyway，本初始化包不可直接覆盖其现有 migration。先检查 `flyway_schema_history`，再用**新增**版本做变更；只有可丢弃的本地测试库才允许清空重建。
